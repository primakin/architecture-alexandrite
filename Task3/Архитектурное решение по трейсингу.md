# Системы, которые следует покрыть трейсингом
На данный момент в системе есть проблема с жизненным циклом заказов, поэтому трейсами следует покрыть следующие сервисы:

- CRM API
- MES API
- Shop API

Данные трейсинга:

- Идентификаторы сервиса и инстанса
- Эндпоинт/метод
- Идентификаторы запроса и заказа
- Время поступления запроса в сервис
- Время обработки запроса
- Результат выполнения запроса (изменение статуса заказа, код ошибки и т.п.)

# Мотивация
Трейсинг помогает быстро находить причины проблем, например, медленной работы сервиса и потери сообщений. Из этого следует, что после внедрения трейсинга:

- Вырастет удовлетворенность клиентов (CSAT, NPS)
- Сократится Time to market (TTM) засчет ускорения багфикса
- Сократится Mean time to recovery (MTTR)
- Снизится Error rate


# Предлагаемое решение
Для реализации трейсинга используем OpenTelemetry + Jaeger. Внедряем SDK OpenTelemetry в приложения (Shop API, CRM API, MES API) и настраиваем отправку трассировок в Jaeger. Для хранения трассировок используем Elasticsearch. На стороне CRM API и MES API потребуется также реализовать распространение контекста через RabbitMQ.

# Компромиссы
- Для хранения трассировок придется поднимать Elasticsearch, а это потребует дополнительных ресурсов. На первом этапе можно обойтись развертыванием all-in-one образа Jaeger с хранением трассировок в памяти.
- Трейсинг не принесет пользы, если проблема заключается, например, в неоптимальном алгоритме расчета заказов на стороне MES - в этом случае будет эффективнее локальная отладка с профайлером.

# Безопасность
- Предполагаем, что в системе уже внедрен RBAC. В этом случае для просмотра трейсов у учетной записи должна быть роль "Аудитор".
- Чувствительные данные (ФИО клиента, пароли и т.п) не должны попадать в трейсы в открытом виде.
