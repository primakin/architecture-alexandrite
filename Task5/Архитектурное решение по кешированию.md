# Мотивация
Для операторов критически важно видеть актуальный список заказов, т.к. от этого зависит и их вознаграждение, и то, насколько быстро заказ будет взят в работу и выполнен. Следовательно, есть смысл кешировать информацию о заказах на стороне MES API. Это должно решить проблему медленной загрузки страницы со списком заказов (и для операторов, и для внешних пользователей API), тем более, что фильтр по статусам и пагинация не помогли. Также кеширование снизит нагрузку на БД MES.

Можно было бы реализовать кеширование и для 3D-моделей, т.к. файлы могут быть достаточно объемными. Но скорее всего, чтение файла модели во время расчета стоимости заказа происходит только один раз - если так, то в кешировании смысла нет.

# Предлагаемое решение
Реализуем серверное кеширование на стороне MES API. У нас read-heavy сценарий (за весь жизненный цикл заказа его статус меняется ~10 раз, а сам заказ выполняется примерно за месяц), поэтому выбираем между Cache-Aside, Read-Through и Refresh-Ahead.

Предлагаю остановиться на Cache-Aside, т.к. этот вариант проще в реализации (минимум изменений в MES API при ограниченном количестве C#-разработчиков) и отказоустойчив (при падении кеша продолжаем работать с БД напрямую). Read-Through подходит меньше из-за чувствительности к ошибкам и необходимости прогрева кеша. Refresh-Ahead пока выглядит избыточным из-за сложности реализации и отсутствующей (пока) системы мониторинга. В будущем можно рассмотреть этот вариант, если Cache-Aside будет не хватать.

## Стратегия инвалидации кеша
Инвалидируем кеш по ключу (номер заказа). При изменении статуса только одного заказа нам не надо сбрасывать в кеше весь список. Проблемы могут возникнуть, если один заказ входит в несколько списков (например, списки по разным фильтрам). Но можно предположить, что команда реализовала фильтрацию и пагинацию на стороне фронтенда - в этом случае кешироваться будет только один список (все заказы). Если же фильтрация реализована на стороне MES API, больше подойдет инвалидация по запросу - в этом случае при изменении одного заказа будем сбрасывать все списки, в которых есть этот заказ.
Также используем TTL на случай сбоя инвалидации по ключу/по запросу. Для начала можно установить TTL = 5-10 минут, за это время список заказов не успеет критично устареть.
