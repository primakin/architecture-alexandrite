# Планирование логирования
- Shop API
    * INFO - пользователь завел новый заказ
        + время
        + идентификатор покупателя
        + номер заказа
    * INFO - пользователь создал/загрузил 3D-модель
        + время
        + идентификатор покупателя
        + номер заказа
        + идентификатор 3D-модели
    * INFO - пользователь оформил заказ (нажал на кнопку "Сделать заказ")
        + время
        + идентификатор покупателя
        + номер заказа
- CRM API
    * INFO - заказ подтвержден
        + время
        + номер заказа
        + идентификатор продавца
    * INFO - заказ завершен
        + время
        + номер заказа
        + причина - закрыт вручную или по сообщению от транспортной компании
- MES API
    * INFO - система посчитала стоимость заказа
        + время
        + номер заказа
        + стоимость
    * INFO - оператор взял заказ в работу
        + время
        + номер заказа
        + идентификатор оператора
    * INFO - оператор выполнил заказ
        + время
        + номер заказа
        + идентификатор оператора
    * INFO - оператор начал упаковывать заказ
        + время
        + номер заказа
        + идентификатор оператора
    * INFO - заказ отправлен покупателю
        + время
        + номер заказа
        + идентификатор оператора
        + адрес доставки
        + трек номер

TRACE/DEBUG используем при разработке и для отладки в тестовом окружении. Например, для отладки алгоритма расчета заказа в MES.

WARN для логирования предупреждений, например, "Пользователь неправильно ввел пароль".

ERROR для логирования ошибок, например, "Заказ не найден", "Невозможно расчитать стоимость заказа", "Некорректная 3D-модель".

FATAL для логирования сбоя сервисов и оборудования.

# Мотивация
Как и в случае с трейсингом, логирование помогает быстро находить причины проблем, например, с "подвисшими" и потерянными заказами. Из этого следует, что после внедрения логирования:

- Вырастет удовлетворенность клиентов (CSAT, NPS)
- Сократится Time to market (TTM)
- Сократится Mean time to recovery (MTTR)
- Снизится Error rate

Логирование и трейсинг в первую очередь нужно настраивать для MES API, т.к. именно на этом уровне происходит больше всего изменений статусов заказов, расчитывается стоимость заказа, а также осуществляется работа с очередью. Соответственно, больше вероятность найти причину проблем с "подвисанием" заказов именно на этом уровне.

# Предлагаемое решение
Для логирования используем ELK:

- Filebeat агрегирует данные из разных источников и передает их в Logstash - конвейер данных.
- Logstash передаёт данные в Elasticsearch - базу данных.
- Elasticsearch обменивается данными с Kibana, инструментом для визуализации.

## Политика безопасности в отношении логов
- Предполагаем, что в системе уже внедрен RBAC. В этом случае для просмотра трейсов у учетной записи должна быть роль "Аудитор".
- Чувствительные данные (ФИО клиента, пароли и т.п) не должны попадать в логи в открытом виде.

## Политика хранения в отношении логов
- Для каждого сервиса создаем отдельный индекс.
- Логи прод окружения (INFO) храним минимум 90 дней, т.к. пользователи жалуются, что выполнение заказа задерживается на несколько месяцев. Соответственно, для решения подобных проблем нужны логи за весь период.
- В тестовом окружении по-умолчанию включаем логи уровня TRACE/DEBUG и храним их две недели, т.к. команда работает двухнедельными спринтами. Для багфикса и отладки такого объема логов должно хватить.
- Размер индексов - достаточный для хранения логов за указанные выше периоды.

# Система анализа логов
Надо настроить алертинг для следущих сценариев: 

- Резкое увеличение количества ERROR (например, +100% за час).
- Любой FATAL, связанный с отказом оборудования.
- Падение количества оформленных заказов (например, -50% за сутки).
- Отрицательные или нулевые суммы заказа.

Поиск аномалий:

- Много неудачных попыток логина с одного IP.
- Всплеск ошибок 401 или 403 - попытки доступа к чужим заказам/данным.
- Аномально высокая частота запросов к каталогу с одного IP может говорить о попытке парсинга каталога.
